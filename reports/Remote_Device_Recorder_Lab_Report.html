Preserving recorded data when the connection disappears

I deployed two Ubuntu Server virtual machines in VirtualBox to simulate a remote recording station and an office monitoring system. Two sensor processes saved readings locally, queued them during connection outages, and synchronized them after communication returned. A separate virtual disk held scheduled queue backups for a controlled restoration test.

03 / DEPLOYMENT PROCESS

Start collection and establish the baseline

First, prepare Python and the lab directory on each guest and upload the supplied scripts from Windows. Create the monitor certificate with its host-only IP in the Subject Alternative Name, generate a private token, and transfer only the public certificate and shared token to OutdoorVM. Retain the TLS private key on MonitorVM.

# Each guest

python3 tests.py

# MonitorVM, after certificate and token setup
bash install-services.sh collector
# OutdoorVM: enter 192.168.56.102 at the prompt
bash install-services.sh outdoor

Recording and delivery process

Each agent generates a unique reading ID and UTC timestamp, saves the reading to its SQLite outbox, and attempts an authenticated HTTPS delivery. The collector commits accepted IDs before acknowledging them. The agent then removes acknowledged queue entries. Scheduled backups preserve queue state; the collector is the ongoing record after delivery.

# Windows: keep this terminal open
ssh -N -L 8080:127.0.0.1:8080 azureuser@192.168.56.102
# Browser: http://localhost:8080

The setup capture records seven successful offline logic tests. The live baseline confirms that both sensor processes deliver readings to the monitoring system.

04 / BACKUP PROCESS

Keep recoverable queue snapshots

Identify the new empty backup VDI with lsblk and verify its attachment before formatting. The helper creates and mounts an ext4 filesystem at /mnt/field-backup and records a persistent mount. Run an initial backup, then enable the timer. This creates versioned snapshots; it does not mirror every new write continuously.

# OutdoorVM: verify the NEW empty disk first
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
# In this lab the verified backup device was /dev/sdb
bash prepare-backup-disk.sh /dev/sdb
python3 backup.py
sudo systemctl enable --now field-backup.timer
findmnt /mnt/field-backup

The final export reports an approximately 7.8 GiB ext4 backup filesystem with 7.4 GiB available and three snapshot versions per sensor. Backups run approximately every 30 seconds and provide recoverable queue copies; the selected snapshot successfully restored all four pending readings. To further reduce exposure between snapshots, the backup interval can be shortened. A future synchronous-replication extension could acknowledge protection only after each reading is committed to both primary and independent secondary storage.

For stronger fault isolation in a physical deployment, place the secondary copy on a separate physical storage device and verify restoration from that copy. This extends the lab’s working snapshot-and-restore process.

05 / CONNECTION OUTAGE

Interrupt delivery while recording continues

Keep both sensors running. In an OutdoorVM terminal, block only telemetry traffic to the monitor. In a second SSH terminal, inspect local queue counters while the dashboard shows stale readings. Let the helper restore the rule, then confirm current readings and drained queues.

# OutdoorVM terminal 1 — controlled link test
cd ~/field-lab
bash outage.sh 192.168.56.102 120

# OutdoorVM terminal 2
date -u
python3 agent.py --status --db data/sensor-a.db
python3 agent.py --status --db data/sensor-b.db

The 120-second invocation provides a repeatable test window. The exported journals identify the observed delivery failures, queue growth and successful recovery acknowledgement.

06 / QUEUE EVIDENCE

Measure the backlog and verify delivery

The local terminal captures pending records rising above zero and later returning to zero. The exported journals add finer detail: both agents reached eight pending records, then each acknowledged a batch of nine at 04:06:55 UTC. The ninth includes a newly sampled reading at recovery.

Measured sequence: first logged failure at 04:05:38; pending reaches 8 at 04:06:48; acknowledged=9 and pending=0 at 04:06:55. The 77 seconds from the first failure to success includes detection and retry timing, rather than directly measuring the link outage.

At the outdoor export, generated and acknowledged counts are equal for both sensors and pending/rejected are zero. Independent ID reconciliation found every one of the 867 unique IDs logged as queued in the supplied journals in the later collector CSV.

07 / SENSOR PROCESS FAILURE

Keep one sensor reporting when another stops

Stop only Sensor A and keep Sensor B running. After the freshness threshold passes, compare their dashboard states, then restart A. The result demonstrates process-level continuity: Sensor B continues reporting while Sensor A is interrupted, and Sensor A resumes reporting after it starts again.

# OutdoorVM
sudo systemctl stop field-sensor-a
# Wait at least 35 seconds; inspect the dashboard
sudo systemctl start field-sensor-a

# Separate process-crash test
sudo systemctl kill --kill-whom=main --signal=SIGKILL \
  field-sensor-a.service
sudo journalctl -u field-sensor-a -n 30 --no-pager

What the journal confirms

UTC eventObserved result
04:13:06 → 04:13:12Sensor A killed with signal 9, then service started again: 6 seconds.
04:14:24 → 04:14:29A second signal-9 termination is followed by restart: 5 seconds.
04:15:44 → 04:19:37Sensor A intentionally stopped and subsequently started. Sensor B has no matching stop during this interval.

An intentional systemctl stop does not trigger the same automatic restart path as an unexpected process failure. The logs support both distinctions. A later status export shows NRestarts=0 for the current service invocation; that final value does not erase the historical restart events in the journal.

08 / RESTORATION PROCESS

Restore a saved queue and check its IDs

During a separate connectivity interruption, pause both sensors and the backup timer so the recovery point stays stable. Take a consistent snapshot, preserve the original queue file rather than deleting it, and restore Sensor A to the original database path. Restart collection and restore connectivity.

# OutdoorVM, while telemetry is blocked
sudo systemctl stop field-sensor-a field-sensor-b
sudo systemctl stop field-backup.timer field-backup.service
python3 backup.py
# Select the latest A snapshot and preserve it as:
# recovery-evidence.sqlite
# Keep the original primary database before restoring
mv -n data/sensor-a.db data/sensor-a.before-restore.db
python3 recover.py --snapshot recovery-evidence.sqlite \
  --output data/sensor-a.db
sudo systemctl start field-sensor-a field-sensor-b
sudo systemctl start field-backup.timer

09 / POST RESTORATION

Observe synchronization settling back to normal

The recovery screenshots capture two different stages and are both useful. The first records the historical backlog reported by a newly received sample. The next shows a subsequent reading with no queue reported. Neither image alone is an instantaneous view of remote disk state.

The journals place both sensor stops at 04:33:57 UTC and both starts at 04:37:27. At 04:37:47 each acknowledges seven records and has pending=0. This is consistent with delivery of buffered records after the controlled restoration sequence.

The selected snapshot contains four recoverable pending readings. Pausing the processes establishes a stable recovery point, and restarting them resumes sampling and synchronization. Independent matching confirms that all four snapshot IDs reached the collector.

APPENDIX A / REPRODUCTION

Reproduce the workflow with the actual addresses

These commands summarize the process using the lab’s observed address plan. Use the reproduction reference alongside the setup guide, verify new disks before formatting, and preserve prior recovery files.

1 Prepare and transfer

# Each guest, once OpenSSH and Python are installed
mkdir -p ~/field-lab/data

# Windows PowerShell in the script folder
$OutdoorIP = "192.168.56.101"
$MonitorIP = "192.168.56.102"
scp .\*.py .\*.sh "azureuser@${OutdoorIP}:/home/azureuser/field-lab/"
scp .\*.py .\*.sh "azureuser@${MonitorIP}:/home/azureuser/field-lab/"

2 Configure and validate

# MonitorVM: generate certificate with IP SAN
MONITOR_PRIVATE=192.168.56.102
openssl req -x509 -newkey rsa:2048 -sha256 -days 30 -nodes \
  -keyout collector.key -out collector.crt \
  -subj /CN=field-lab-monitor \
  -addext "subjectAltName=IP:${MONITOR_PRIVATE}"
chmod 600 collector.key
openssl rand -hex 32 > token.txt
chmod 600 token.txt
bash install-services.sh collector

Transfer collector.crt and token.txt to OutdoorVM through the Windows host; keep collector.key on MonitorVM. Remove the temporary Windows token copy after successful transfer. On OutdoorVM run install-services.sh outdoor and enter 192.168.56.102. Verify service status and the dashboard before injecting failures.

3 Capture and export before shutting down

# OutdoorVM
sudo -v
python3 export_evidence.py outdoor
# MonitorVM
sudo -v
python3 export_evidence.py monitor
# Download and open BOTH archives locally. Then on each VM:
sudo poweroff
